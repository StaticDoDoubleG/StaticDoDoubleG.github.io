# 프로젝트와 머신러닝 적용 설계

## 1. PVE 과부하 사전 예측
EX1 프로젝트 자료의 중심 주제는 Proxmox VE(PVE)의 CPU·메모리 시계열을 이용해 약 5분 뒤 과부하를 예측하는 이진 분류다. 초기 검증은 PVE 노드 단위로 시작하고, 데이터와 시간이 충분하면 VM 단위로 확장한다. 모델은 예측과 분석에만 사용하며 자동 스케일링이나 운영 설정 변경은 범위 밖이다.

## 2. 수집 파이프라인
권장 흐름은 `PVE API 또는 pve_exporter → Prometheus → Grafana → Python`이다. 단기 확인은 PVE API/RRD로 시작하고, 장기·다중 지표 저장에는 Prometheus를 사용한다. Grafana는 수집 상태와 실험 구간 확인에 쓴다.

- 권장 수집 주기: 1분
- 권장 기간: 최소 2주, 가능하면 3주
- 핵심 지표: CPU 사용률, 메모리 사용률
- 보조 지표: 디스크 I/O, 네트워크, load average, 실행 중 VM 수
- 인증 토큰, 호스트명, IP 같은 민감정보는 분석 데이터에서 제거한다.

## 3. 라벨과 특징
초기 기준의 한 예는 CPU 80% 이상 또는 메모리 85% 이상이 최근 5분 중 3분 이상 지속될 때 과부하로 정하는 것이다. 이 기준과 임계값은 실험 전에 고정해야 한다.

시간 $t$의 입력은 최근 구간의 측정값과 변화량으로 구성한다.
- 입력: `t-5분~t`의 CPU·메모리 수준, 이동 평균, 최대값, 증가량
- 정답: `t+1분~t+5분` 안에 과부하가 발생하는지 여부

`정확히 t+5분`의 임계값을 예측하는 단순 라벨링도 가능하지만, 최종 보고서에서는 둘 중 하나를 명확히 선택해야 한다.

## 4. 시간 순서와 데이터 분할
시계열에서는 과거로 미래를 예측해야 하므로 무작위 분할을 피한다. 앞 구간을 train, 그 뒤 구간을 validation, 가장 뒤 구간을 test로 둔다. 미래 데이터의 통계량으로 과거를 전처리하지 않도록 scaling도 train 구간에서만 fit한다.

## 5. 모델과 평가
항상 정상으로 예측하는 기준선을 먼저 만든 뒤 다음 모델을 비교한다.
- 기준 모델: Logistic Regression
- 해석 가능한 비교 모델: Decision Tree
- 확장 모델: MLP 또는 Random Forest 중 하나

과부하 사례가 적을 수 있으므로 accuracy만으로 판단하지 않는다. 재현율은 실제 과부하를 놓치지 않는 정도, precision은 경보의 정확도, F1은 둘의 균형을 나타낸다. 혼동행렬과 함께 오탐·미탐 사례를 분석하고, 부하 유형별 성능도 비교한다.

## 6. 통제 부하 실험
격리된 테스트 VM에서 정상·부하 구간을 반복해 데이터를 만든다.
- CPU: `stress-ng`, `sysbench`
- 메모리: `stress-ng`
- 디스크 I/O: `fio`
- 네트워크: `iperf3`

예시 순서는 정상 30분 → 단일 부하 10분 → 정상 20분이며, 강도와 순서를 바꿔 특정 패턴 암기를 줄인다. 실제 서비스 VM과 호스트에는 부하를 주지 않는다.

## 7. 수업 개념과의 연결
- Logistic Regression은 Sigmoid와 BCE를 연결한다.
- MLP는 hidden layer, 활성화 함수, Cross Entropy, 역전파를 사용한다.
- 시간순 validation/test는 train/test 분할과 일반화 개념을 적용한다.
- 과적합은 weight decay, dropout, 조기 종료 등으로 점검한다.

## 8. 대안 주제
`DX.md`에는 MNIST 활성화 함수 비교, Fashion-MNIST, UCI 회귀·분류 데이터, Digits에서 K-NN·SVM·Decision Tree·MLP 비교 등의 후보도 있다. 각 주제는 동일한 흐름인 데이터 정의 → 시간/무작위 분할의 적절한 선택 → 기준 모델 → 지표 비교 → 오분류 분석으로 설계한다.

# 08. UNIX 프로세스 생성과 제어

지난 게시글에선 프로그램, 프로세스, 그리고 스레드의 차이에 대해 다뤄보았다. 이제 프로세스를 생성하고 제어하는데에 있어 알아야 하는 내용을 다뤄볼 것이다.

## 프로세스와 문맥 전환

운영체제는 프로세스 제어 블록(PCB)에 PID, 부모 PID, 스케줄링 정보, 메모리 Context, 열린 자원 등을 보관한다. <br>
한 CPU에서는 한 순간에 하나의 프로세스만 실행되지만, 운영체제는 현재 상태를 저장하고 다음 프로세스의 상태를 복원하는 Context Switch로 여러 프로세스를 운영한다.

Context Switch는 시스템 콜, 장치 인터럽트, 타이머 인터럽트와 같은 사건으로 시작된다. 프로세스는 PID와 PPID를 갖고 부모-자식 계층을 만든다. [첫 게시글]()에서 다룬 셸이 명령을 실행하는 구조가 대표적인 예다.

`fork`는 쉽게 말하면 분기를 생성하는 함수(시스템 콜)다.<br>
UNIX 시스템에서는 분기의 원본을 부모, 분기의 결과물을 자식이라고 부른다.<br>
~부모 프로세스가 먼저 사라져버리면  자식 프로세스를 고아라 부른다. 매서운 컴공 ㅠㅠ~

`fork`로 만들어진 자식은 부모의 속성과 자원을 상당 부분 상속하지만 완전히 같은 프로세스는 아니다. 자식은 새로운 PID를 받고 부모 PID도 새 관계에 맞춰 설정된다.

이 때 상속되지 않는 예외 요소는 아래와 같다.

- **PID와 PPID**: 자식은 고유한 PID를 받고 자신의 부모를 가리키는 PPID를 갖는다.
- **CPU 사용 시간**: 부모의 누적 CPU 시간을 그대로 물려받지 않는다.
- **프로세스가 보유한 lock**: 부모가 잡고 있던 잠금을 자식이 그대로 보유하지 않는다.
- **alarm 타이머**: 부모의 남은 알람 시간이 자식에게 그대로 적용되지 않는다.
- **펜딩 시그널(Pending Signal)**

반면 주소 공간의 내용, 환경, 열린 파일 같은 많은 실행 정보는 자식에게 전달된다. `fork`는 모든 속성을 똑같이 복사하는 함수가 아니라, 상속 규칙에 따라 새 프로세스를 만드는 함수다.

## `fork`의 반환값과 주소 공간

```c
pid_t pid = fork();
if (pid < 0) {
    perror("fork");
    return 1;
}
if (pid == 0) {
    /* 자식 프로세스 */
} else {
    /* 부모 프로세스: pid는 자식의 PID */
}
```

- `-1`: 자식 생성 실패
- `0`: 자식에서 반환
- 양수: 부모에서 반환되며 생성된 자식의 PID

부모와 자식은 `fork` 호출 다음 명령부터 각각 실행한다. `fork`된 자식이 main부터 실행되지 않는다는 말이다.<br>
주소 공간은 복제되지만 일반적으로 copy-on-write 방식으로 관리되므로, 한 프로세스가 변수를 수정해도 다른 프로세스의 같은 이름의 변수 값이 자동으로 바뀌지는 않는다.

## 프로세스 생성 패턴

프로세스 생성 코드는 한 번의 `fork`로 끝나지 않고 반복될 수 있다.

- **단순 분기**: 부모와 자식이 서로 다른 코드를 실행한다.
- **체인(chain)**: 자식이 다시 `fork`해 부모-자식 연결이 길게 이어진다.
- **팬(fan)**: 하나의 부모가 여러 자식을 만들어 작업을 분배한다.

반복문 안에서 `fork`를 호출하면 생성되는 프로세스 수가 빠르게 늘 수 있다. `n`회 분기한다고 해서 항상 원하는 수의 프로세스만 생기는 것은 아니므로, 부모와 자식이 어느 반복을 계속하는지 조건을 명확히 작성해야 한다.

## `wait`와 실행 동기화

`fork` 직후 부모와 자식은 concurrent하게 실행되므로 누가 먼저 끝날지 알 수 없다. 부모가 자식의 종료를 기다려야 하면 `wait` 또는 `waitpid`를 호출한다.

```c
int status;
pid_t child = wait(&status);
if (child == -1) {
    perror("wait");
}
```

`wait`는 단순한 시간 지연이 아니라 자식 상태가 바뀔 때까지 부모를 대기 상태로 전환하는 동기화다. 자식이 언제 끝날지 모를 때 `sleep(1)`을 사용하는 것은 보장된 방법이 아니다. 종료 여부를 반복해서 검사하는 busy waiting은 CPU를 계속 사용한다.

종료 상태는 다음 매크로로 해석한다.

- `WIFEXITED(status)`: 정상 종료
- `WEXITSTATUS(status)`: 정상 종료 상태값
- `WIFSIGNALED(status)`: 시그널에 의한 종료
- `WTERMSIG(status)`: 종료를 일으킨 시그널

부모가 종료한 자식의 상태를 회수하지 않으면 좀비 프로세스가 남을 수 있다. 여러 자식의 작업을 모은 뒤 다음 단계를 진행해야 하는 경우 부모가 모든 자식에 대해 `wait`를 수행한다.

## `exec`의 역할

`exec` 계열 함수는 현재 프로세스의 프로그램 이미지를 다른 실행 파일로 교체한다. PID와 프로세스 자체는 유지되지만 text, data, stack 등 실행 내용은 새 프로그램으로 바뀐다.

```c
execl("/bin/ls", "ls", "-l", (char *)NULL);
perror("execl");
```

`exec`가 성공하면 호출한 함수는 반환하지 않는다. 따라서 바로 다음 오류 처리는 `exec` 실패 때만 실행된다.

- `l`: 인자를 목록으로 전달
- `v`: 인자를 배열로 전달
- `p`: `PATH`를 검색해 실행 파일을 찾음
- `e`: 환경 배열을 호출자가 지정

`p` 계열에서는 첫 번째 인자에 경로가 없어도 `PATH`에 등록된 디렉터리를 검색한다. `e` 계열은 `name=value` 문자열 배열로 새 환경을 지정한다.

## 셸과 백그라운드 프로세스

셸은 일반적으로 다음 순서로 외부 명령을 실행한다.

1. 셸이 `fork`로 자식 프로세스를 만든다.
2. 자식이 필요하면 표준 입출력을 리다이렉션한다.
3. 자식이 `exec`로 요청된 프로그램을 실행한다.
4. 부모 셸이 `wait`로 자식 종료를 기다린다.

백그라운드 명령은 부모 셸이 자식의 종료를 즉시 기다리지 않고 다음 명령을 받을 수 있게 한다. 장시간 실행되는 데몬은 터미널과 분리되어 백그라운드에서 서비스를 지속하는 프로세스다. `Ctrl+C` 같은 인터럽트 문자가 어떤 프로세스 그룹에 전달되는지도 포그라운드·백그라운드 동작과 관련된다.

## 파일 디스크립터 상속

자식은 부모가 열어 둔 파일 디스크립터를 상속한다. 부모와 자식의 디스크립터가 같은 열린 파일 상태를 가리킬 수 있으므로 파일 offset과 파이프의 EOF 조건에 영향을 준다. 사용하지 않는 디스크립터를 닫지 않으면 읽는 프로세스가 EOF를 받지 못할 수 있다.

그럼 다음과 같은 의문이 생길 것이다.<br>
부모가 자식을 fork하기 전에 fd를 닫으면 문제가 없겠지만(자식한테 상속되기 전에 fd 테이블에 해당 fd가 없을 것이므로) fork하고 나서 fd를 닫으면 어떻게 되는 걸까?<br>

이는 `fork()`가 실행되는 과정을 다시 곱씹어보면 된다.<br>
`fork()`가 실행되는 순간 자식 프로세스는 부모의 파일 디스크립터 테이블을 **그대로 복사하여 독립된 자신만의 파일 디스크립터 테이블**을 가지게 된다.<br>
부모가 fd를 지우면 부모 자신의 테이블 엔트리에서만 해당 fd가 사라지며해당 열린 파일을 가리키는 커널의 시스템 파일 테이블(System File Table) 참조 카운트(Count)가 1 감소할 뿐이다. <br>
결론적으로 자식 프로세스의 파일 디스크립터 테이블에는 디스크립터가 여전히 **유효**하게 남아있으므로, 자식은 아무런 문제 없이 해당 파일이나 파이프를 통해 읽기/쓰기 작업을 계속할 수 있다.

또한, 이렇게 사용하지 않는 디스크립터가 있는 경우 fd를 지워줘야 하는데, 그 이유는
- 파이프에서 `read()`를 수행하는 프로세스가 **EOF(0바이트 읽기)** 를 반환받으려면, 시스템 파일 테이블 상에서 해당 파이프의 쓰기 전용 디스크립터(Write End)를 가리키는 모든 참조 카운트가 **0**이 되어야  한다. 
- 그런데 부모가 fd를 안 지우고 있으면, 자식이 fd를 다 쓰고 반환해도 커널은 참조카운트를 0이 아닌 상태로 둘 것이므로, 자식이 읽는 파이프 내부 데이터가 다 비워져도 EOF를 받지 못하고 block 상태에 빠지게 된다.

예시 코드로 다시 확인해보면
1. `fork()` **전에** `open()` 호출 (파일 offset 공유)

```c
#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>

int main(void) {
    char c = '!';
    int myfd;

    // 1. fork 전 부모가 파일을 열음
    if ((myfd = open("my.dat", O_RDONLY)) == -1) {
        perror("Failed to open file");
        return 1;
    }

    // 2. 프로세스 복제 (파일 디스크립터 테이블 상속)
    if (fork() == -1) {
        perror("Failed to fork");
        return 1;
    }

    // 3. 부모와 자식이 같은 파일 옵셋을 공유하며 읽기 수행
    read(myfd, &c, 1);
    printf("Process %ld got %c\n", (long)getpid(), c);
    return 0;
}
```
`my.dat` 내용이 `ab`일 때, 한 프로세스가 `'a'`를 읽으면 파일 옵셋이 1 증가하므로, 다른 프로세스는 `'b'`를 읽게 되므로, `Process 1001 got a` / `Process 1002 got b`와 같이 출력되어야 한다.

2. `fork()` **후에** 각각 `open()` 호출 (독립된 파일 Offset)

```c
#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>

int main(void) {
    char c = '!';
    int myfd;

    if (fork() == -1) {
        perror("Failed to fork");
        return 1;
    }

    // 부모와 자식이 각각 독립적으로 open 호출
    if ((myfd = open("my.dat", O_RDONLY)) == -1) {
        perror("Failed to open file");
        return 1;
    }

    read(myfd, &c, 1);
    printf("Process %ld got %c\n", (long)getpid(), c);
    return 0;
}
```
`my.dat` 내용이 `ab`일 때, 양쪽 프로세스 모두 파일의 0번 위치부터 읽기 시작하므로 `Process 1001 got a` / `Process 1002 got a`와 같이 출력되어야 한다.

3. 사용하지 않는 디스크립터를 닫지 않으면 읽는 쪽 프로세스가 EOF(`0`)를 받지 못하고 무한 대기
```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

int main(void) {
    int fd; // fd: 읽기 전용, fd: 쓰기 전용
    pid_t pid;
    char buf;

    if (pipe(fd) == -1) {
        perror("pipe error");
        exit(1);
    }

    pid = fork();
    if (pid < 0) {
        perror("fork error");
        exit(1);
    }

    if (pid == 0) { 
        // [자식 프로세스: 읽기 전용]
        close(fd); // 쓰기용 디스크립터 즉시 닫기 (필수)

        // 부모가 쓰기 디스크립터를 모두 닫고 전송을 끝내면 read()는 0(EOF)을 반환함
        ssize_t bytes_read;
        while ((bytes_read = read(fd, buf, sizeof(buf) - 1)) > 0) {
            buf[bytes_read] = '\0';
            printf("[자식 수신]: %s\n", buf);
        }

        close(fd); // 사용 완료 후 읽기 디스크립터 닫기
        exit(0);
    } else { 
        // [부모 프로세스: 쓰기 전용]
        close(fd); // 읽기용 디스크립터 즉시 닫기 (필수)

        char msg[] = "Hello from Parent!";
        write(fd, msg, strlen(msg));

        // 부모가 쓰기 작업을 완료한 후 쓰기 디스크립터를 닫아야 자식이 EOF를 받음
        close(fd); 
    }

    return 0;
}
```
부모가 데이터를 다 보낸 후 `close(fd)`을 호출하면 커널 내 해당 쓰기 끝의 **참조 카운트가 0**이 되어 자식 프로세스의 `read()`가 비로소 **EOF(`0`)** 를 읽고 반복문을 빠져나오게 된다.

## + 파이프(Pipe) 양방향 통신 시 구조

단일 파이프로 양방향 통신을 시도하면 **자신이 쓴 데이터를 자신이 읽는 경쟁 상태(Race condition)** 가 일어난다. 따라서 양방향 통신을 할 때는 반드시 **2개의 파이프**를 생성해야 한다.

* **파이프 1 (Parent → Child)**: 부모는 쓰기만, 자식은 읽기만 수행
* **파이프 2 (Child → Parent)**: 자식은 쓰기만, 부모는 읽기만 수행
